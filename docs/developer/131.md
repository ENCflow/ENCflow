## 131. ダムの運転則の拡張: 実績の再生(放流量・貯水位の時系列)と、履歴を持たない実務の操作規則(制限水位・洪水調節開始流量・放流量の上限)(2026-11-26 設計合意・実装。無効時はビット一致)

利用者向けは users_guide/structure.md「ダム・湖沼」の「実務の操作規則」「実績の再生」と hydraulics.md §4(日英)。
検定は test/damops。残りの作業は handoff 1i。族の設計の正本は §22(ダムは「ダム(&list_struct_dam。族の第四号)」と
「ダム・湖沼への一般化」)。

### 131.1 経緯(利用者の問い)

利用者の問いは 4 つだった。(1) 3 つの運転モードのほかに、独自の運転則を Fortran のユーザールーチンとして実装
できるようにする意味はあるか。(2) 実務の運転判断に要る状態量はモデルにそろっているか。(3) それをユーザールーチンから
取れるか。(4) 過去の再現計算で当時の操作の実績を正確に再現するには、パラメータファイルに操作の時系列を書く拡張より、
ユーザールーチンに直書きするほうが自由度が高くないか。

検討の結論(会話で比較と推奨を示し、利用者が「提案通り進めたい」と合意):

- **実績の再生には時系列入力が適する**。放流量 Q(t) はどちらに書いても同じ時系列で、直書きで足せるのは条件分岐
  だけだが、再生に分岐は要らない。直書きは、出水やダムを足すたびのリビルド、結果から入力をたどれないこと
  (fn_structure は init_resultdir が結果ディレクトリへ写すが、手元で書き換えたソースは残らない。方針 13)、
  数値の確かめにくさ、CI の検査の外に出ることが不利。さらに実際の操作は規則どおりとは限らない(特別防災操作・
  臨機の判断)ので、規則をコードに書いても実績にはならない。実績の正本は記録された時系列である。
- **再現で本当に難しいのは自由度ではなく、モデルの流入量と記録の流入量のずれ**。何を記録に合わせるか(放流量か
  貯水位か)の選択になるので、時系列のモードを 2 つにする。
- **実務で広く使う規則は形が決まっている**ので、組み込みのモード(パラメータ)にする。ただし今回は履歴を持たない
  範囲(下の 131.2)。
- **ユーザールーチン**(またはダムの量を BMI で公開して外から運転する案)は、運転則そのものの研究(仮想の操作、
  予測雨量による事前放流、複数ダムの統合運用など)の需要が残るなら、位置づけの議論を経てから作る。利用者向け文書は
  ユーザールーチンを「理想化実験用で、実データの計算では使わない」と位置づけており(users_guide/user_routines.md)、
  ダムのフックは時間ループの中で呼ばれる最初のフックで、実データで使う最初のフックにもなる。開発目的 2 の
  「設定ファイルの追加・変更だけで」と方針 13 にも関わる。先送り(handoff 1i)。

状態量の棚卸し(会話の表の要約):

| 量 | モデル内 | ダムの運転則から(実装前) |
|---|---|---|
| 貯水位・貯水量・流入量 | ある(流入はその歩の捕捉帯の吸収量 ÷ dt。捕捉帯への直接降雨は 1 歩遅れ) | 読める(dam_operate は par_sum_rows の後で全ランク同値) |
| 時刻・暦 | ある(s%t、date0_c) | 渡せば読める |
| 流入の増減・ピーク通過、前の歩の放流量 | ない(§22: 履歴を持たない設計)。dqout は保存対象外の診断値 | 読めない(dqout はリスタート直後に 0) |
| 下流基準点の水位 | ある(担当ランクだけが持つ) | 読めない(集める仕組みがない) |
| 下流基準点の流量 | 測線の流量は m_record の私有 | 物理側が読むのは §24.1 の観測者規律に反する |
| 流域雨量・予測雨量 | 集水域の定義と集計がない / モデルの外の情報 | 読めない |

フックを作る場合の要件(記録として残す): スカラーは引数で渡せる。空間の値は namelist で宣言した参照セルを
枠組みが集めて渡す(structure_makebdc の代表セルの収集 = 担当ランクだけ値を入れて総和、と同じ型)。履歴は
枠組みがダムごとに持ち、私有 save(paddy.dat・sfm.dat と同じ。save_version 付き)で保存する(ルーチン内の save
変数はリスタートで戻らず、ネストの複数インスタンスでも共有されてしまう)。ルーチンが返すのは目標放流量だけにし、
死水の下限・スピル・質量保存・放流セルへの分配は枠組みに残す。

同時に見つけた既存の挙動: モード 1 は流入が q0 未満でも q0 を放流する(vt = q0·dt、vrel = min(vt, V − Vmin))ので、
dam_h_init を HV の最低点より上に置くと、洪水の前に最低水位まで下げる。利用者向け文書は「多目的ダムは制限水位を
明示」と案内していたので、その通りに設定すると利水容量まで洪水調節に使う計算になる。モード 2 は小さな流入から
(1 − r)·Qin を貯め始める。→ 制限水位 dam_hlim を足し、起動時の注意(note:)で知らせる。モード 1 の式は変えない
(注意は表示だけで結果は変わらない)。

### 131.2 決定(2026-11-26。利用者の選択)

利用者の選択: 範囲は「時系列の 2 モードと、履歴を使わない実務の規則」、規則の形は「モード 1・2 に省略可能な
パラメータを足す」、モード 5 の初期水位の省略時は「時系列の開始値」(3 つとも推奨案)。

1. **f_dam_mode = 4(放流量の時系列 dam_qout_val / fn_dam_qout_val)と 5(貯水位の時系列 dam_h_val /
   fn_dam_h_val)**。書式は境界条件の時系列と同じ(namelist は (分, 値) の折れ線で秒へ換算、ファイルは各行
   "時刻(min) 値" で read_val_file2、ファイルが優先、interp_series の線形補間、範囲外は端の値)。時刻は
   dam_operate を呼ぶときの s%t = この歩の終わりの時刻(境界条件の時系列と同じ時相)。同じ時刻の点を重ねると
   段になる(interp_series は後ろの点から補間を始める)ので、時刻の減少だけを止める(read_dam_series)。
   - 4: vt = Q(t)·dt。床は Vmin(死水)、スピルは従来どおり。Q < 0 は init で停止。
   - 5: vt = max(vnow − V(H(t)), 0)。この歩の終わりの貯水量が目標水位の貯水量になる。流入が足りなければ放流 0。
     H は最低水位〜サーチャージの範囲を init で検査する(目標が範囲内ならスピルは起きない)。dam_h_init の省略時は
     H(t0)(記録の水位から立ち上がりなく追従する)。
   - 4・5 は但し書きなし(記録に含まれる。dam_tadashigaki を書くと停止)。
   - 4 は追加の放流工(dam_lake)にも使える(取水量の記録など。dam_draw に case (4) を足した)。5 は追加の放流工に
     使えず、5 の湖沼を参照する追加の放流工も停止する。主放流が目標水位に合わせて放流した後に追加の放流工が引くと、
     水位が目標からずれるため(2 つの運転が同じ水位を決め合う)。記録の全放流量を湖沼本体に与える。
2. **制限水位 dam_hlim(モード 1・2。追加の放流工も可)**: 運転の放流の床 vfl = V(hlim) を t_structure に持ち、
   clamp を vrel = min(vt, max(vnow − vfl, 0)) にした。省略時は vfl = geom(1) = Vmin で、式も値も従来と同じ
   (ビット一致)。hmin ≤ hlim < htad(床の上で但し書きが始まる順序)。モード 1 + dam_hlim は河川砂防技術基準の
   一定量放流方式(流入 < q0 は水位を保って流入を流し、超えると q0 で貯める。洪水後は q0 で床へ戻る)になる。
   床より下から始めた場合は、床に達するまで放流しない(貯め戻す)。
3. **洪水調節開始流量 dam_qon と放流量の上限 dam_qmax(モード 2)**: dam_rate_target が目標を返す。
   Qin ≤ Qon なら Qon(床では clamp により流入をそのまま流して水位を保ち、床より上なら Qon で床へ戻す)、
   Qin > Qon なら min(Qon + r(Qin − Qon), Qmax)。Qin = Qon で連続。どちらも指定がなければ従来の
   reff = r + (1 − r)·ramp の経路のまま(ビット一致)。指定ありの経路の但し書きは vt + ramp·max(a − vt, 0)
   (モード 1 と同じ形。Qon = 0・上限なしなら従来の式と代数的に同じ)。dam_qmax はモード 3(c) と同じ「計画最大
   放流量」の名前を、モード 2 では上限に使う(既存の入力でモード 2 に dam_qmax を書いたものはなかった)。
   Qmax ≥ Qon、Qmax ありはサーチャージ水位が必須(上限を超えた流入を貯めるため)、素通し湖沼には書けない。
4. **モードと合わない指定は止める**(黙って捨てない): dam_qon はモード 2 だけ(モード 1 では q0 自体が調節開始の
   流量)、dam_hlim はモード 1・2 だけ、時系列はモード 4・5 だけ。水位固定湖沼(モード 0)への指定も止まる。
5. **起動時の注意(note:。表示だけ)**: モード 1 か dam_qon つきのモード 2 で、初期水位が最低水位より高いのに
   dam_hlim がないとき、運転の放流が最低水位まで下げ得ることを知らせる。モード 4 で dam_h_init がないとき、
   空虚から始まることを知らせる。

状態は増えない(時系列は init で読み、再開時も読み直す。履歴なし)ので、save 形式は変えていない。方針との突き合わせ:
物理量(記録の放流量・水位、操作規則の値)を直接与える(方針 12)、入力は境界条件と同じ単純な書式(方針 11)、
有効化は f_dam_mode の値で、新しいパラメータを書かなければ従来の経路(方針 7・8)、出典・限界の明記と検定
(方針 13)。方針に反する点はない。

### 131.3 出典と独自の部分

出典: 国土交通省 水管理・国土保全局 (2019) 河川砂防技術基準 計画編 技術資料、施設配置等計画編 第2章 第2-1章
第3節 貯水池(ダム)の 3.1.2 洪水調節方式・3.1.3 洪水調節容量(平成31年3月版)。

- 一定率一定量放流方式: 洪水調節開始流量以上の流入量に対し、ピーク流量に達する流量までは流入量の一定割合を、
  ピーク流量に達した流量以降は一定量を放流する調節方式。
- 一定量放流方式: 洪水波形等にかかわらず一定量の放流を行う、いわゆるピークカット方式。
- ほかに自然調節方式(モード 3)と不定率調節方式(持たない)。
- 洪水調節容量は平常時最高貯水位または洪水貯留準備水位から洪水時最高水位までの間で確保する(dam_hlim は
  この下端にあたる)。同じ節の推奨に、洪水の発生が予想された時点で事前に放流して洪水調節容量を確保すること
  (持たない)。

独自(出典は方式を言葉で定めている): 式の形(開始流量を超えた分に率を掛け、開始流量で連続にする)、ピーク後の
一定量を持たない簡略化(ピークの判定に履歴が要る)、洪水後に Qon(モード 2)・q0(モード 1)で床へ戻す扱い、
上限 Qmax。ピーク後も式のまま放流が下がるので、実際の規則より多く貯める(貯水位は高めに出る)。利用者向け文書の
「できないこと」に書いた。

### 131.4 検証(2026-11-26。gfortran 13.3、Open MPI 4.1.6、Intel Xeon(AVX-512))

- **既存の経路のビット一致**(変更前のソース 8ba02f2 から作った実行ファイルとの比較): test/damwq(モード 1)の
  全出力がバイト一致。既存のパラメータだけで組んだ臨時のケース(モード 1 の但し書きの近く、線形 HV のモード 2 の
  但し書き、3(a)・3(b)・3(c)、素通し、水位固定、追加の放流工 3 種)の全出力がバイト一致。
- **新しい検定 test/damops**(Check_damops.py。7 基。詳細は README): 記録行ごとに運転則の式・時系列と一致
  (モード 1・2・追加の放流工は床より上で式に一致、床では下限と上限の間。モード 4 の放流と 5 の水位は時系列の
  補間値と印字の桁 f13.4 の範囲で一致)、流入 = 1 歩前のソースの流量、Log の S × 有効面積 = 初期貯水量 +
  ソースの累計体積(差 2.2e-13 m)、165 分で保存して再開した計算のダム CSV と S が通し計算と一致、モードと合わない
  設定など 9 通りが起動時に止まる。reference はこのマシンで作った(新しいケース)。比較は test/damwq と同じく
  既定 ULP = 1(CPU の違うマシンで S の最終桁が変わり得る)、同じマシンでは ULP = 0 で一致。
- **MPI**: np = 1, 2, 4 が逐次 reference と ULP = 0(np = 4 では 5 つの捕捉帯が別のランクに分かれる)。
- **-Og -fcheck=all**(nightly の debug ジョブと同じフラグ。作業用の複製で): 逐次の Run.sh 全体(rules・restart・
  停止の検査)が実行時エラーなしで合格、np = 2 が debug 逐次とビット一致。
- トップレベルの make(utils のリンク)が通る。params_index・consistency・devdocs・i18n の検査(CI の i18n.yml と
  同じ条件)と各ツールの単体テストが合格。test/damops は CI(ci.yml の逐次・np = 2)と nightly の REF_CASES に登録した。
