## 10. 回帰テスト運用

- reference は環境依存(ビット一致基準)なので gitignore。**make clean では
  消さない**(clean 後の初回実行が未検証の結果を黙って新基準にする事故を防ぐ)。
  更新は明示的に `./Run.sh -u`。作成・更新時に env/BUILDINFO.txt へ実行環境
  (ホスト・module・ldd・ビルドモード)を自動記録する。
- param.txt は正規化(コメント除去)して比較し、不一致なら SKIP(比較不能)。
- 基準を更新したら、その結果の妥当性をプロットで一度は目視確認する。
- **np=2 以上の -fcheck=all ビルド実行を検証階段の必須段とする**。確保縮小
  後は帯外アクセスと引数の要素数不足が実行時に名指しで検出される
  (get_diff_v1 の並び結合バグはこの段で捕捉できた種類。§12 参照)。
- **確保範囲を変える変更の後は、最適化ビルドより先に -fcheck np>=2 を回す**。
  帯外のゴミ読みは結果を「少しだけ」壊す(落ちずに、もっともらしい値のまま
  最終数桁が狂う)ので、回帰テストの不一致から遡るより境界検査の方が早く
  正確に原因を指す。n_valcells の sw 帯外読み(S がセル1個分の定数比で
  ずれた)がこの型の実例。静的データを実際に使うケース(実地形+粗度+
  河道)で回すこと。wave(固定値 z0/rn0)はこの検査の感度が低い。
- 計測(m_record)付きケースでは FILES に record CSV を加えて比較する
  (例: `FILES="Log.txt fluxes/flux0001.csv"`)。点集約方式は
  ランク数によらず CSV がビット不変なので ULP=0 で比較できる。
  測線がランク境界を跨ぐ配置を意図的に含めること(点集約の急所)。
- benchmark 系(解析解あり)は環境非依存の解析解ベーステストとして test/vshaped に昇格させ、CI に
  載せた(2026-11-10。§104。examples/benchmark/v-shaped の 20 m の 2 ケースを Check_vshaped.py で判定)。
- **record・出力・save 等のファイル形式を変更したら utils/ の該当ツールを
  確認する**。utils/ は一部(rerecord 等)を除き読み書きを独立実装しており、
  回帰テストの網の外にあるため、形式変更に黙って取り残される。libencflow を
  リンクするツールも再ビルドが必要(形式は共有するが自動追従はしない)。
- **SKIPCOLS の列番号はケースの Log ヘッダに依存する(実バグ 2026-09-15)**:
  Runge 列は S(m) 形式では4列目、S_surf/S_grnd/S_total 形式では**6列目**。
  拡張ヘッダの8ケース(frost/pump/conduit/coastal_drain/gwseep/kdpart/
  sewer_wq/splash)が SKIPCOLS=4 のままで、S_grnd を誤って除外し Runge を
  比較していた(coastal_drain/gwseep/kdpart は np 実行時に Runge 差で FAIL、
  他は偶然一致で潜伏)。SKIPCOLS=6 へ修正し、逐次+np=1,2,4 の PASS を確認
  (gfortran 13.3/OpenMPI 4.1.6)。新ケースの Run スクリプトを雛形から
  複製するときは Log ヘッダと列番号の対応を必ず確認すること。
- **CI は二層構成(2026-09-15 導入)**: 毎 push の ci.yml(高速5ケース×
  逐次/np=2)+夜間の nightly.yml(reference 全14ケース(dambreak 追加後)の逐次と
  MPI np=1,2,4、トップレベル make による utils 追随漏れ検出、
  -Og -fcheck=all ビルドの逐次=np2 一致検査、BMI 適合性 bmi-tester
  +BMI 経由実行の CLI ビット一致。bmi ジョブは wave の bmi-tester と
  等価性に加え、test/bmi_nest(2026-10-10 追加)と test/bmi_vars
  (2026-10-25 追加)の受け入れ試験を回す)。debug 層は release(-Ofast/
  -flto)製のコミット済み reference と比較できないため、ランナー内で
  debug 逐次の reference を作り直して MPI 結果と照合する(リポジトリの
  reference は不変 — 消去・再生成はランナーの使い捨て作業領域のみ)。
- **CI の高速ケースの検定スクリプトは標準ライブラリだけで書く(2026-11-08)**: ci.yml は gfortran・make(MPI のジョブは
  OpenMPI も)だけを入れ、numpy は入れない(nightly の bmi ジョブだけが pip で入れる)。test/stg の Check_stg.py が
  numpy を読んで main の ci.yml(45205ab)の逐次のジョブを落としたので、bil(float32)を array で読む形に直した。
  ci.yml に加える検定型のケース(prmap・wfswash・gwlateral・gwtani・stg)の Check_*.py は、numpy のない Python で
  確かめてから加える(sys.modules['numpy'] = None として実行すると、手元でも ImportError を再現できる)。
- **CI のランナーを ubuntu-24.04 に固定(2026-11-05。利用者の決定)**: GitHub の ubuntu-latest が 2026-11-05 に
  ubuntu-24.04 から ubuntu-26.04 へ切り替わり(コンパイラは gfortran 13 から 15 へ)、ci.yml の vzcol の Log.txt が
  1 量子(相対 2e-14)で reference と不一致になった(逐次・MPI np = 2 とも。main の d5aa81a・8977ce5。開発 VM の
  gfortran 13.3 では 4 スレッド・1 スレッドともバイト一致で、スレッドによる揺らぎではない)。reference は
  開発 VM の gfortran 13 で作るので、ci.yml・nightly.yml のコンパイルするジョブの runs-on を ubuntu-24.04 に
  固定した(i18n.yml は Python の検査だけなので ubuntu-latest のまま)。固定の後の main(d83c164)の ci.yml は
  逐次・np = 2 とも 16 ケースが合格(vzcol は identical)。ランナーのログに出る apt の gfortran の版
  (4:13.2.0・4:15.2.0)はメタパッケージの版で、コンパイラの版ではない(開発 VM の Ubuntu 24.04 では同じ
  4:13.2.0 で、実体の gfortran-13 は 13.3.0。325618a・d83c164 の説明の「gfortran 13.2」はこの取り違え)。
  gfortran 15 への移行は、reference の生成環境ごと移す別の判断(ubuntu-24.04 のランナーが提供される間の措置)。
- **sewer_wq は同一バイナリ以外との ULP=0 比較が成立しない(既知
  2026-09-15)**: release(-Ofast/-flto)では逐次/MPI 二つのバイナリの
  ビルド差(演算並べ替え)が Runge サブステップ回数の閾値敏感性で増幅され、
  S_surf と wq.csv(in_gwc_g 等)に相対 ~5e-6 の差が出る(np=1 でも同じ。
  debug 逐次 vs release reference でも同型の差)。-Og ビルドでは逐次=np2 が
  ビット一致であることを確認済み = MPI 実装のバグではなくビルド差起因。
  **2026-10-02 決定: RTOL=1e-5 で判定する。** 同じ敏感性が release 逐次層
  にも波及した(Nightly #18: 開発 VM で作った reference と GitHub ランナーの
  逐次 release ビナリが相対 4.9e-6 で不一致。VM 上の同一コミットの逐次
  release はビット一致 = make.inc の -Ofast -march=native -flto がホスト CPU
  で異なるコードを生成するビナリ差)。reference を作り直しても生成環境
  以外では再発するため、test/sewer_wq の Run.sh / Run_MPI.sh に RTOL=1e-5
  (環境変数で上書き可)を明示し、nightly の release MPI 層へ戻した。
  実装バグの検出(逐次=np2 のビット一致)は -Og -fcheck=all 層が RTOL=0 を
  与えて担うので検出力は落ちない。あわせて
  Compare_ref.sh が CSV の区切りカンマ付きトークン("値,")を数値として
  扱うようにした(従来は文字列比較に落ち、wq.csv には RTOL/ULP の許容が
  効いていなかった。既存ケースは全て ULP=0・RTOL=0 なので合否は不変)。
  reference の BUILDINFO.txt の mode 行は src の直近ビルドのスタンプで
  あり、実行したビナリのモードではない(誤読注意)。
- **ビルド差による reference 11 件の更新(2026-10-31。利用者の指示)**:
  reference を持つ 36 件を現行ソースの release 逐次で回すと全件 PASS だが、
  11 件(dambreak・kdpart・sewer_wq と nhwave・nhwave_nh・nhsolitary・
  nhcurrent・nhshelf・nhbore・nhbreak・nhbottom)がビット一致でなく許容差内
  だった(比較外の Runge 列、ULP=1 の最終桁、sewer_wq の RTOL=1e-5)。
  原因は次の 2 段で切り分けた。(1) reference を作った時点のソース
  (c71a578・5aa1e71)を同じ環境で release ビルドすると、nhshelf 以外の 10 件の
  reference がバイト単位で再現する = 環境は同じ。(2) make.inc の FFLAGS を -O2
  (fast-math・-march=native・LTO なし)に置き換え、作成時点と現行のソースを
  比べると 11 件とも出力がバイト一致する = 計算は不変。差は無関係な変更に
  よる -Ofast/-flto のコード配置のずれ(上の sewer_wq の項と同型)。作成時点の
  ソースは git worktree で取り出す。確認のうえ ./Run.sh -u で更新した。10 件の
  新しい reference は更新前の実行(別のプロセス)の出力とバイト一致する。
  nhshelf だけは事情が違う。NH ソルバの 4 スレッドの実行間非決定(§71・§81)で
  実行のたびに最終桁と Runge 列が揺れるうえ、2026-10-24 の reference は別の
  環境で作られていて、この環境では 1 スレッドでも 1 要素が 2 量子ずれる
  (ULP=1 で不合格)。そこで nhshelf の reference は **OMP_NUM_THREADS=1 で**
  作り直した(1 スレッドの再実行で identical。4 スレッドの既定の実行は
  ULP=1 の範囲で揺れる)。検定を 1 スレッドに固定する案(1 回が約 4 分から
  約 12 分に延びる)は採らず、既定のスレッド数のまま ULP=1 で判定する
  (利用者の判断)。更新後の 11 件は MPI np=1, 2, 4 でも PASS。
  Runge 列(比較外)だけのずれや許容差内の差は不一致ではなく、更新するかは
  人間が決める(規律1)。
- **damwq の reference 比較を ULP=1 に、nightly の MPI 層の制限時間を 90 分に(2026-11-25。利用者の決定)**:
  Nightly #74(main の 98efcfc)の full regression (MPI np=1, release) が test/damwq で落ちた。Log.txt の S が
  1:00 と 1:15 の行で 0.05000000000001(reference は 0.05000000000000。1 量子、相対 2e-13)、wq.csv は identical。
  同じ不一致は Nightly #71(11-21。np=2 のログで確認。np=4 も同じ時刻に落ちた)にも出ていて、#72(11-22。src も
  reference も #71 と同じ)は全ジョブが合格、#73(11-24)の np=1 は damwq を通っている。逐次のジョブは 4 晩とも
  合格。np にも src の変更にも対応せず、ジョブが載ったランナーで決まっている。
  - **原因**: make.inc の `-Ofast -march=native -flto` がホスト CPU ごとに別のコードを作る(上の sewer_wq の項、
    §90.18 と同じ)。damwq の S は丸め誤差の積み重ねで 0.05 から増え、1:00 以降は 0.05 + 5.0e-15 = 印字(小数
    14 桁)の丸めの境目にちょうど乗る。同じソース(29b1e39。src は 98efcfc と同じ)を `-march` だけ変えて
    ビルドすると(gfortran 13.3。この作業環境の `-march=native` は sapphirerapids)、sapphirerapids・
    icelake-server・skylake-avx512 は reference とバイト一致し、znver2・znver3・znver4・haswell・x86-64-v3 は
    Nightly の不合格と同じ 2 行が同じ値でずれる(逐次も MPI np=1 も同じ)。S を小数 18 桁で出す確認用のビルド
    (別の木で印字の書式だけを変えたもの。14 桁に丸めると元のビルドの印字と一致)では、1:00 の S − 0.05 が
    native で 4.968e-15、znver3 で 5.024e-15 で、差は 6e-17(相対 1e-15)。終了時の状態の保存(state.dat・
    swflow_enc.dat・wq.dat)は sapphirerapids と icelake-server でバイト一致し、znver3 とは一致しない
    (並列化ではなく生成コードの差)。H・C の分布と wq.csv は、印字の桁ではどのビルドも同じ。ランナーの CPU の
    型はログに出ないので、「AMD(または AVX2 まで)の CPU のランナーに載ったジョブが落ちる」は、これらの
    ビルドとの一致からの推定である。
  - **影響の範囲**: REF_CASES の 23 ケースのうち chichibu・chichibu_cond を除く 21 ケースを znver3 のビルドで
    流すと(1 スレッド。逐次と MPI np=1)、落ちるのは damwq だけだった(逐次の wfdoppler は途中で止めた。
    MPI np=1 は合格)。native の MPI np=1 は 21 ケースとも合格。chichibu・chichibu_cond(どちらも ULP=1)は
    znver3 で確かめていない。
  - **決定**(sewer_wq の 2026-10-02 の決定、§90.18 と同じ考え方): test/damwq の Run.sh・Run_MPI.sh の
    reference 比較を `ULP=${ULP:-1}` にする。reference は変えない。同じマシンでは `ULP=0 ./Run.sh`
    (`ULP=0 ./Run_MPI.sh N`)でビット比較でき、CLAUDE.md の検証規律(逐次 reference に ULP=0)はこの形で
    確かめる。ビルドの差は S で 6e-17(0.006 量子)で、印字が変わるのは丸めの境目をまたぐときだけなので、
    差は 1 量子を超えない。nightly の -Og -fcheck=all 層には `export ULP=0` を足し、許容を持つケース(damwq・
    wfcurrent・wfsed と、Run_case.sh の MPI の既定 ULP=1 に従う dambreak)でもビット一致を要求する(#74 の
    debug 層のログでは 23 ケースの全ファイルが identical で、合否は変わらない)。
  - **採らなかった案**: CI のビルドの `-march` を固定する(たとえば x86-64-v3)。ランナーの CPU によらない
    結果になるが、reference を全部そのビルドで作り直すことになる。この作業環境の CPU もセッションで変わる
    (§90.18 のときは cascadelake、今回は sapphirerapids)。コミット済みの reference は AVX-512 の Xeon の
    結果で、AMD の CPU の環境では、手元の実行でも同じ型の最終桁の差が出うる。
  - **制限時間**: full-mpi の np=1 は回帰テストだけで約 58 分かかる(1 プロセス・1 スレッド)。#72 はジョブ
    全体で 59 分 41 秒(60 分の制限に 19 秒の余裕)で通り、#71 と #73 は 60 分で打ち切られた(#73 は apt の
    導入に 14 分かかった)。full-mpi の `timeout-minutes` を 60 から 90 にした(np=2・4 は 33〜45 分)。
  - **検証**: 変更後のスクリプトで、native のビルドは逐次(4 スレッド)と MPI np=1・2・4 が identical
    (`ULP=0` を付けても同じ)。znver3 のビルドは逐次と MPI np=1・2・4 が「2 small differences within
    tolerance」で合格し、`ULP=0` を付けると Nightly と同じ 2 mismatches で不合格になる。nightly.yml は YAML と
    して読め、full-mpi の制限が 90 分、debug 層の実行行に `export ULP=0` が入っている。ランナーでの実行は、
    main に入った後の最初の Nightly で確かめる。
