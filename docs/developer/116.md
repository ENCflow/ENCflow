## 116. developer.md の分割: 基本方針の独立(docs/policy.md)と節ごとのファイル化(2026-11-22。利用者の依頼と、推奨案での合意)

### 116.1 背景

- docs/developer.md が 2.8 MB・29,609 行・116 節(§0〜§115)・約 148 万字になり、GitHub で表示できなく
  なった(Markdown の表示の実用上の上限は約 500 KB と報告されている。公式の仕様値ではない)。
- 開発者向けの文書だが、一般向けの文書から多数参照されている。リポジトリ全体の「developer.md」への言及は
  約 2,700 件(約 980 ファイル)で、そのうち一般向けの文書(users guide・例題と検定の README・List_samples。
  日英)からが約 1,400 件(約 400 ファイル)。§0 を指すのは 15 件だけで、大半は設計記録の節を式・既定値の
  出典として指す(方針 13 の説明責任の仕組み)。一般向けに書かれた内容は §0 だけ(§34 公開体制・§35 文書の
  構成方針も確かめたが、保守する人向けの決定記録)。
- 開発時の文脈の消費: 全体は 100 万トークン級で一度には読めず、grep で位置を探して部分的に読んでいた。
  節の境目が見えにくく、関係の薄い前後まで読みがちだった。
- 中身の偏り: §0 は 12 KB、§1〜§15(規約)は 101 KB、§16〜§67 は 758 KB、§68〜§115 は 1.95 MB(全体の
  69%。移流項・河道の調査の記録が大半。§110 は 343 KB、§68 は 291 KB)。

### 116.2 決定事項

1. §0 を docs/policy.md(正本)として独立させ、英訳 docs/en/policy.md を全体のミラーにする(旧
   docs/en/developer.md の §0 の部分ミラーを移した)。
2. §1〜§115 は節ごとに 1 ファイル docs/developer/NNN.md に置く(NNN は節番号を 3 桁にしたもの)。本文は
   変えない。
3. docs/developer.md は目次にする(§0 の案内・引用と記録のしかた・テーマ別の索引・全節の一覧)。
4. 節番号は恒久の識別子とし、既存の「developer.md §N」の形の引用は書き換えない(目次から 1 回でたどれ、
   §N のファイルは番号から機械的に決まる)。§0 への参照は、利用者向けの文書(日英)と開発の案内(CLAUDE.md・
   architecture.md・multilingual.md・handoff の未完了の項目)だけ policy.md に改めた。plan 文書の当時の
   記録とソースのコメントは改めない(目次の §0 からたどれる)。
5. 旧 URL の docs/en/developer.md は、目次の §0(policy.md への案内)の部分ミラーとして残す(外から張られた
   リンクの受け皿)。
6. 目次のテーマ別の索引に、テーマごとの「現行」(いまの仕様を書いた利用者ガイドの章と、現在の既定・設計を
   決めた節)と「記録」を置く。既定値の出どころはソースの宣言(list_enc.f90 ほか)と照合した。
7. tools/devdocs/check.py を CI(i18n.yml)に加える(目次・ファイル名・見出しの一致、引用の解決、Markdown の
   大きさ)。
8. 運用の規則: 新しい節は新しいファイルに起こし、目次に 1 行足す。既存の節への追記はその節のファイルの末尾に
   小節で足す。200 KB を超えた節には追記せず新しい節を起こす(§110 から §111〜§115 を分けたやり方の明文化)。
   Markdown は 400 KB まで(CI で不合格)。

### 116.3 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| テーマ別に十数ファイル | 移流項のテーマだけで約 1 MB になり、さらに分ける必要がある。§68 のように複数のテーマにまたがる節の置き場所を決められず、新しい節ごとに置き場所の判断が要る。§N からファイルを引くのに毎回目次が要る |
| 番号の範囲で数ファイル | §110 を含む束は単独でも 343 KB を超える。内容のまとまりがなく、末尾の束が太り続ける |
| 引用を全部新しいパスへ書き換える | 約 980 ファイル(Fortran のコメント・param を含む)が変わり、翻訳の確認記録 204 組がすべて stale になって確認のやり直しになる。得られるのは目次を 1 回経由しないことだけ |
| 題名入りのファイル名(068_advection.md など) | 一覧で中身が分かるが、名付けの判断が 115 回要り、題名や中身が変わると名前が古くなる。§N から機械的に決まらない |

### 116.4 分割の作業と検証

- 一回限りのスクリプトで分割した(リポジトリには置かない)。空行を除く全行の多重集合が元と一致
  (欠落 0・重複 0)し、各節の行の並びが元と一致することを確かめた。
- 本文の変更は 2 点だけ。(1) §85・§86 の中に追記されていた §84 の小節 84.15〜84.18(当時のファイルの
  末尾に足されたもの。84.15・84.16 は §85 の本文の後、84.17・84.18 は §86.5 と §86.6 の間にあった)を、
  084.md の末尾(84.14 の後)へ移した。これらへの引用 115 件が §84 のファイルで見つかるようにするため。
  (2) 節の中の相対リンク 3 か所(§68・§91・§93)に ../ を付けた(1 段深い場所へ移ったため)。
- リポジトリ内の「developer.md §N.M」の形の引用(改行・コメント記号をまたぐものを含む。2,536 件)が、
  すべて分割後の節・小節に解決する。
- 翻訳の確認記録は、§0 への参照を改めた 11 組を記録し直した(--method assistant)。

### 116.5 落とし穴

- **分割前から作業中のブランチ**: 旧 developer.md の末尾に節を足したブランチをマージすると衝突する。
  足された節を docs/developer/NNN.md へ移し(番号が重なれば付け直す)、目次に 1 行足して解消する。
  ある節の小節を末尾に足していた場合は(§84.15〜84.18 と同じ形)、その節のファイルの末尾へ移す。
- **行ごとの履歴**: GitHub の blame と `git log --follow` は分割をまたいで追えない。分割前の行の履歴は
  `git blame 619cb1f -- docs/developer.md`、変更の履歴は `git log 619cb1f -- docs/developer.md` でたどる
  (619cb1f は分割の直前のコミット)。
- **小節へのリンク**: §N.M へのリンクは §N のファイルまでにする。見出しのアンカーは日本語の題名から作られて
  長く、題名を直すと切れるので使わない。
- **大きな節**: §68(約 15 万字)と §110(約 18 万字)は、分割後も 1 本では読み切れない。テーマ別の索引の
  「現行」から読み、経緯は小節の見出しで探して必要な所だけ読む。

### 116.7 handoff.md の分割(2026-11-22。利用者の依頼「handoff.md も同じように整理してください」)

- 背景: handoff.md も 340 KB(番号付きの 56 項目と、番号のない 3 つの節)あり、作業の初めに読まれるので
  文脈の消費が大きく、CI の Markdown の上限 400 KB にも近かった。
- 決定事項: developer.md と同じ形にした。番号付きの項目(00y・1l・4 など)は 1 項目 1 ファイルで
  docs/handoff/<番号>.md に置き、番号をそのまま識別子(ファイル名)にする。番号のない「公開準備」と
  「中期の道標」の節は、見出しごと publication.md・roadmap.md に移した(中期の道標の箇条は番号を持たない
  ので 1 ファイル)。handoff.md は目次(前置き・書き方・現在の到達点・各節の一覧)にした。「現在の到達点」は
  新しいセッションが最初に読む要約なので目次に残した。内容は削っていない。
- 目次の題名: 各項目の 1 行目の太字(行をまたぐものは改行を空白 1 つにする)。150 字を超える 5 件(00y・
  00w・00u・00n・00l)は、句読点の切れ目で先頭を残して「…」で縮めた(検査は先頭一致)。
- 検査: tools/devdocs/check.py の handoff(一覧とファイル・1 行目の番号・題名の一致、1 ファイル 1 項目、
  相対リンク)。「handoff 00y」の形の引用は検査しない(完了した項目は消す運用で、過去の記録からの参照は
  消えた項目を指してよい)。
- 運用: 番号は付け直さず、使い終わった番号を別の項目に使わない。過去には付け直しと使い回しがあり
  (1r・1s の旧番号は 1k で、いまの 1k は流木)、「handoff 1k」の指す先が時期によって違う。完了したら
  項目のファイルと一覧の行を消し、経過は開発記録の該当する節に書く(従来どおり)。
- 検証: 元の空行以外の行がすべて新しいファイル群にあり(欠落 0)、増えた行は目次の一覧と案内だけ。
  各項目のファイルが元の項目と一致する。分割前の最後の版はコミット 0bad327 の docs/handoff.md。
- 対象外: docs/handoff_gwflow_tani.md は作業メモではなく地下水の設計文書(ソースのコメント・利用者ガイド
  からも参照される)なので、そのままにした。
- 残り: 完了した項目の整理(消すかどうかの判断)はしていない(handoff 00ac)。
- 分割の不具合と修正(同日): 分割のスクリプトは項目番号を「1〜2 桁の数字 + 英小文字 2 字まで」の形で読んでいた
  ため、その形でない番号の項目 2 つを前の項目のファイルの末尾に含めていた(完了した項目の監査で見つけた)。
  3 桁の 000 は 00e のファイルに、英字の後に数字が続く 1n2(開発記録 §48・§86 から「handoff 1n2」で引かれる)は
  1m のファイルに入っていた。それぞれ docs/handoff/000.md・1n2.md に分けて目次に 1 行ずつ足し、検査の番号の形を
  「数字で始まる英小文字と数字の並び」に広げた(前の項目のファイルに紛れ込んだ項目を検出する)。元の handoff.md の
  56 個の番号と項目のファイルが 1 対 1 に対応することを確かめた。内容は失われていなかった。
