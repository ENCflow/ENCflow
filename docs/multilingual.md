# ドキュメント・教材の多言語化規約

[English](en/multilingual.md)

2026-10-23 制定。文書、教材、設定例、表示用資産の配置・更新・確認を定める。
言語方針の決定経緯は [developer.md §34.2](developer.md)、計算と検証の規律は
[CLAUDE.md](../CLAUDE.md) に従う。本書はその運用規約である。

## 1. 正本

**`LICENSE` と `TRADEMARKS.md` だけは英語正本。それ以外の文書・教材・設定例は
日本語正本とし、英語版および将来の他言語版はそのミラーとする。**
入口の表示言語と正本の言語は別である。

| 対象 | 正本 | 翻訳・入口 |
|---|---|---|
| ルート README | `README.ja.md` | `README.md` は英語ミラー(GitHub の表示用。§34.2) |
| ライセンス | `LICENSE`(英語) | 日本語を置く場合は参考訳と明示 |
| 名称・商標 | `TRADEMARKS.md`(英語) | `TRADEMARKS.ja.md` は日本語ミラー |
| 協力案内 | `CONTRIBUTING.md`(日本語) | `CONTRIBUTING.en.md` |
| その他の説明・教材・設定例 | 日本語版 | 対応する言語ディレクトリの翻訳 |

翻訳の冒頭には正本を明示する(英語版は「English mirror of <正本パス>」の刻印。
§34.2)。ミラーは要約版や別の教材ではなく、内容・構成・数式・設定値・注意事項・
結論を保つ翻訳である。内容修正は正本から行う。訳文だけの誤訳・表現修正では原文を
変更しなくてよい。科学的な疑問や既存の不整合は別件として記録し、翻訳時に黙って
修正しない。

コード、機械可読の識別子、データ、既存の権利表示、第三者原文は言語別に別実装を
作らない。これらに英語が含まれても、別の言語版の「正本」を新設する意味ではない。
本規約は LICENSE・TRADEMARKS・NOTICE や第三者の権利表示の内容を変更しない。
プログラムの入出力(パラメータ名・Log・画面メッセージ)は英語固定であり、翻訳の
対象外である(§34.2)。

## 2. 配置

日本語正本を機能別・ケース別の場所に置き、翻訳だけを `en/` 以下へ分離する。
対称性だけのために日本語正本を `ja/` に移動しない。名前・ケース名は翻訳しない。

```text
docs/users_guide/time.md              → docs/en/users_guide/time.md
tutorials/README.md                   → tutorials/en/README.md
tutorials/wave/README.md              → tutorials/wave/en/README.md
tutorials/wave/param_step1.txt        → tutorials/wave/en/param_step1.txt
test/wave_river/README.md             → test/wave_river/en/README.md
examples/List_samples/list_wave.txt  → examples/List_samples/en/list_wave.txt
utils/<tool>/README.md                → utils/<tool>/en/README.md
```

`docs/` はルート直下に言語ディレクトリを挿入する。ケース類では**独立して実行する
単位の直下**へ挿入し、その下の相対配置は保持する。例えば、独立ケースが
`examples/benchmark/<case>/` にあれば訳は同ケース内の `en/` に置く。
一方、`test/wave/notes/detail.md` は `test/wave/en/notes/detail.md` に対応する。
検査ツールは最も近い `Makefile` / `Run.sh` を実行単位の目印とし、既存の対応配置も
認識する。目印のない新しい配置は導入時に対応先を確認する。

ルートの README・CONTRIBUTING・TRADEMARKS は上表の例外を維持する。
`CLAUDE.md` も既存の入口を維持し、本規約を参照する。
単一ファイルだけの英語版に使ってきた接尾辞方式(`test/README.en.md`、
`examples/README.en.md`、`bmi/README.en.md`、`utils/<tool>/README.en.md`)は
有効なまま維持する(検査は WARN で示すだけで、移行を要求しない)。新規の
翻訳は `en/` 方式で置き、接尾辞方式を新たに増やさない。他言語も `fr/`、`zh-CN/`
等、同じ規則で追加する。新しい言語コードを導入するときは検査ツールの `LOCALES`
にも登録し、別の言語の監査でその翻訳を日本語正本と誤認しないようにする。

## 3. 翻訳と共有の境界

| 種類 | 扱い |
|---|---|
| README、解説、手順、図のキャプション | 翻訳する |
| namelist 設定例 | 必要なものをコメントのみ翻訳する |
| 数値計算本体・実行・入力生成・検証スクリプト・Makefile | 共通。言語別に複製しない |
| DEM、降雨、境界入力、reference、save/restore、計算結果 | 共通。翻訳対象にしない |
| 文字に依存しない図 | 同じファイルを参照する |
| 言語ラベルを含む図・表示設定 | 必要な場合だけ言語別資産を許可する |
| Notebook | 説明セルを翻訳。コードセルはコメントと表示用の文字列以外を共通に保つ |

対象の範囲は次のとおり。翻訳を要求しない正本は `tools/i18n/scope.json` に
パターンで登録し、監査では `not-required` として扱う(訳が存在する組には影響
しない)。

- `docs/` の利用者向け文書(users_guide、install、tutorial、comparison、ai_guide、
  windows、本書)は全件を対象にする。開発者向け文書(developer.md、handoff、
  `*_plan.md`、`*_design.md`、channel_model.md、architecture.md、icon/)は対象外
  (§34.2。国際化の実態を見て再判断)。
- `tutorials/` は説明と注釈付き入力をセットで扱い、全件を対象にする。
- `test/` のケース説明(README)は順次すべてを対象とする。パラメータのコメント
  英訳は、理解に役立つものから任意で整備する。README に埋め込む図は、図化
  スクリプト(Fig.py 等)の `en` 引数で英語ラベル版を `en/figs/` に描き、英語版
  README はそれを参照する(2026-10-24。描画処理とデータは共通で、切り替わるのは
  ラベルと出力先だけ。引数なしの動作は従来どおり)。
- `examples/List_samples/` は注釈自体がリファレンスなので全件を対象にする。
- `examples/<case>/` の README(現象別例題)も全件を対象にする(2026-10-23 に
  §34.2 を改定)。param・図化スクリプト・図は共有し、コメント英訳は任意。
  benchmark の list_*.txt は対象外。

### 表示用資産

例えば `tutorials/chichibu/en/figs/` や `en/Fig_chichibu.plt` のような既存の英語表示用
資産を、実行資産の重複と混同して削除しない。画像に使う数値・形状・座標・単位・
範囲・データ処理は共通とし、差はラベル等の表示に限定する。
新規整備では共通の描画処理とラベル定義の分離を優先する。ただし既存スクリプトの
共通化は、翻訳追加とは別の変更として検証する。

翻訳のためにモデルを再実行して reference や元の計算結果を差し替えない。
同じ保存済み結果からラベル違いの図を描くことは許可する。
図化ファイルの同等性は自動で保証できないので、原文・表示用ファイル・必要なデータの
版を確認する。確認記録にない共有依存ファイルの変更は自動追跡されない点に注意する。

### Notebook

Markdown セルは翻訳する。コードセルは、コメント(`#`、埋め込み namelist の `!`)と
表示用の文字列リテラル(print の文言など)だけを翻訳してよく、それ以外のコード・
値・パス・セルの種類と順序は同一に保つ(設定例の「コメント以外は完全一致」と同じ
規律)。コード側の多言語対応が必要なら共通コードに実装し、別の変更として検証する。
保存済み出力があるだけでは実行確認済みとしない。公開前に実際の作業場所と実行順序を
確認する。日本語版から説明セルや警告を削った別教材を「ミラー」と呼ばない。

## 4. 実行場所と入力の同一性

**全言語でケース直下を作業ディレクトリにする。`en/` に移動して実行しない。**
Markdown のリンクは文書の位置を基準にするが、コマンドと入力パスは作業場所を基準にする。

```bash
cd tutorials/wave
make
./encflow param_step1.txt       # 日本語コメントの入力
# または、同じ作業場所で
./encflow en/param_step1.txt    # 英語コメントの入力
```

上記は代替手順であり、別々の出力を保存する手順ではない。
同じ出力先を使うので、同じ作業コピーで続けて実行すると結果を上書きし得る。
比較には別の作業コピーを使い、翻訳のために `dir_result` 等を変えない。

翻訳で変えられるのはコメントの自然言語部分だけである。
namelist 名、変数名、数値、文字列値、論理値、パス、代入順序、有効・無効を保持する。
コメントアウトされた設定例の数値・識別子・順序も保持する。
`fn_*` の参照先も変えない。複数ファイル入力では、英語コメントの入口から共有の
正本設定を読む場合がある。すべてのコメントが英語の作業コピーを作る機能は、
この翻訳処理に紛れ込ませず別途設計する。

`test/<case>/Run.sh` と `Run_MPI.sh` は従来の正本入力を使用する。
英語版に合わせて検証条件や reference を切り替えない。英訳入力の直接実行と、
公式の検定・回帰テストは区別する。

## 5. リンクと旧配置の移行

同じ言語の本文が存在する場合は、その本文ファイルへ明示的にリンクする。
単にケースディレクトリへリンクすると日本語 README に戻り得る。
未翻訳なら「(in Japanese)」等を明記し、正本を案内する。
正本・言語選択へのリンクは例外として言語をまたいでよい。
英語正本の法的文書(LICENSE、TRADEMARKS.md)は英語ミラーからそのまま参照する。

移動時には相対リンク・画像リンクを修正する。コードブロック内のコマンドや
パラメータ値を一括置換しない。見出しアンカーは言語ごとに確認する。
旧 `README.en.md` を `en/` へ移す場合、旧位置に短い移動案内だけを残し、本文を
二重保守しない。案内には `<!-- i18n-redirect -->` を付ける。これは検査用の印であり、
自動転送機能ではない。

## 6. 確認記録

「正本の変更 → 翻訳の更新 → 内容確認 → 対応版の記録」を基本とする。
更新できない翻訳は未確認・未更新のまま明示する。ハッシュだけを更新して完了扱いにしない。

`tools/i18n/reviews.json` に原文・訳文の SHA-256、確認者、確認方法(`human` /
`assistant`)、日付を記録する。テキストは UTF-8、改行 CRLF を LF に正規化して
ハッシュ化し、画像等のバイナリはバイト列をハッシュ化する。AI の確認を人間の確認と
して記録しない。

| 状態 | 意味 |
|---|---|
| `missing` | 翻訳がない |
| `not-required` | 翻訳がなく、`scope.json` で対象外と定めた正本(§3) |
| `unreviewed` | 翻訳はあるが対応版の記録がない |
| `reviewed` | 記録した原文・訳文の両方と一致する |
| `stale` | 記録後に原文が変わった |
| `translation-changed` | 原文は同じだが訳文が変わった |
| `missing-source` | 原文がない。未登録の孤立した翻訳も対象 |
| `shared-copy` | 実行・入力等の共通資産を言語ディレクトリへ複製している |

`reviewed` は版を照合した記録であって、翻訳の正しさや計算の妥当性の機械的な証明ではない。
既存ミラーを一括で確認済みにしない。記録のない既存翻訳は、存在だけでは最新とも古いとも
断定できないため `unreviewed` とする。`unreviewed` の組の優先順位付けには
`--git-dates`(正本の最終コミットが訳文より新しい組を警告)を使う。

## 7. 検査

Python 3.9 以上の標準ライブラリだけを使用する。計算本体に新たな依存を追加しない。
リポジトリ直下で実行する。

```bash
python3 -m unittest discover -s tools/i18n -p 'test_*.py' -v

# 全体の現状。未翻訳・未確認というだけでは失敗にしない(not-required は --all で表示)
python3 tools/i18n/check.py audit --links --git-dates

# 確認済みと記録した組の更新漏れとリンクを検査(CI が実行する条件)
python3 tools/i18n/check.py audit --recorded-only --strict-recorded --links

# 全体の対応表(生成結果はコミットしない)
python3 tools/i18n/check.py audit --json > /tmp/encflow-i18n-status.json

# 内容確認後、1組ずつ記録する。AI による確認なら --method assistant
python3 tools/i18n/check.py record docs/install.md docs/en/install.md \
  --reviewer '確認者名' --method human
```

自動発見は `docs/`、`tutorials/`、`test/`、`examples/`、`bmi/`、`utils/` の Markdown、
Notebook、`param*.txt` / `list_*.txt` を対象にする。任意名の設定は明示登録できる。
既存の言語別画像・`.plt`・一定の図化 Python ファイルも検出するが、共有画像の全件に
翻訳を要求しない。`vendor/`、計算結果、reference、save、ビルド等は除外する。
Git 作業コピーでは管理対象と未追跡の非 ignore ファイルを調べ、除外された一時ファイルは
対象にしない。自動発見はすべての種類のファイルを理解するものではない。

`--language fr` はフランス語の組だけを検査し、登録済み英訳を混ぜない。
英語監査では、例外として英語正本の法的文書と既存日本語訳も照合する。
`--strict` は未翻訳・未確認も不合格にするため、段階導入時には通常使わない。
終了コードは 0 = 指定条件を満たす、1 = 不合格、2 = 入力・読み取りエラー。

検査の内容と限界:

- **namelist**: 意味解析でなく、文字列を保護した字句比較。有効な入力(コメント除去後)
  は完全一致を要求する(ERROR)。1 行完結のコメントアウト代入例(右辺が値だけのもの)
  も比較する(ERROR)。「`! dt = 0.05 を使う`」のような説明文は代入例とみなさない。
  複数行の例には手動確認が必要(WARN)。
- **Notebook**: セルの種類・順序と、コメント・文字列リテラルを除いたコードの一致を
  調べる(ERROR)。文字列リテラルの違いは WARN(表示用の文言かを人が確認)。実行はしない。
- **Markdown の構成**: 見出しレベルの並びと表の行数の違いを WARN で示す(ミラーは構成を
  保つ)。冒頭 30 行に正本パスの刻印か正本へのリンクがなければ WARN。
- **`--links`**: 通常の Markdown の inline リンク・画像・reference 定義についてローカルの
  参照先と一部の言語取り違えを調べる(GitHub の脚注定義 `[^key]:` は対象外)。完全な
  Markdown パーサではなく、HTML、見出しアンカー、外部 URL の到達性、Notebook 内の
  リンクは未検査。
- 表示用スクリプトや画像の意味の同等性、本文中の数式・数値・コード例は人が確認する。
  静的検査の合格をモデルの実行成功、MPI 一致、reference 一致と呼ばない。

## 8. 運用

- 正本を変えたら同じ作業で翻訳を更新し、内容を確認してから `record` する。更新でき
  ないときは `stale` のまま残し、`docs/handoff.md` に未反映を書く。
- CI(`.github/workflows/i18n.yml`)は単体テストと「記録済みの組の更新漏れ・リンク」
  だけを合格条件にする(2026-10-23 の初回全件監査の結果を確認したうえで導入)。
  未翻訳・未確認の既存文書は失敗条件にしない。`--strict` への移行は、未確認の組が
  整理できた時点で判断する。同じ CI で `tools/params_index/check.py` が全パラメータ索引
  (日英)を `src/*.f90` の namelist 宣言と突き合わせる(欠落・余分・並び・日英の対応・
  項目数の記述・章ページでの名前の記載。developer.md §35.1。2026-10-24 導入)。
- 既存の日本語正本は移動・削除しない。図化処理の共通化や実行機構の変更は翻訳追加と
  分ける。計算本体、正本の数値入力、reference を翻訳作業で変更しない。
- 初回監査で見つかった既存の不整合(英語版 List_samples の更新漏れ等)は
  `docs/handoff.md` に列挙し、翻訳の更新として順次解消する。
