# AI エージェントと使う(利用者向けガイド)

ENCflow は入出力がすべてテキストなので、AI コーディングエージェント
(ターミナルやエディタからファイル操作・コマンド実行までを行う AI)に
**「現象の言葉」で指示してケースを作らせる**ことができます。実際、
ENCflow 自体の開発・検証の多くが AI エージェントとの協働で行われて
います。このページは、開発参加ではなく**利用者としてケース作成・
実行・解析を AI に任せたい方**向けの案内です。

## 始め方

CLI 型のエージェント(例: Claude Code。他の CLI 型・IDE 統合型でも
考え方は同じです)なら、クローンしたリポジトリのディレクトリで
起動するだけで、エージェントがリポジトリ全体(コード・ドキュメント・
例題)を認識します:

```bash
cd ENCflow
claude        # または使っているエージェントの起動コマンド
```

Claude Code の場合は、リポジトリに同梱のスラッシュコマンド
**`/make-case`** が自動で使えるようになっています。ケース作成の
定型手順(下記)が組み込まれているので、まずはこれで試してください:

```
/make-case 融雪と凍土が関わる、春先の融雪出水のような現象
```

> **補足**: `/make-case` は定型手順をまとめた入口にすぎません。
> エージェントには**普段の言葉でそのまま話しかけられます** — 後述の
> 例文はすべてスラッシュコマンドなしの指示文です。既存のケースの
> 修正も「work/mycase/param.txt の粗度 rn0 を 0.03 に変えて再実行し、
> 前の結果と水深分布を比較して」のように言うだけです。対話は続いて
> いるので、結果を見ながら「雨をもっと強く」「図を横並びに」と
> 重ねていけます。多数ケースの一括感度実験、観測に合わせた簡単な
> キャリブレーション、結果レポートの作成のような複合作業も、手順を
> 言葉で説明できるものなら任せられます。

エージェントはファイルの作成やコマンド実行の前に許可を求めてきます
(設定・プランによっては自動承認)。慣れるまでは1つずつ内容を見て
承認するのが安全です。

## どんな指示ができるか

「使う機能の組み合わせ」を自分で調べなくても、現象の言葉で頼めます。
エージェントは[用途集](users_guide/usecases.md)で現象→機能を引き、
[ユーザーガイド](users_guide.md)各章と
[List_samples](../examples/List_samples/) でパラメータを確認して、
ケース(パラメータファイル+必要なら地形等のデータ)を組み立てます。

指示のコツは 3 つです:

1. **成功条件を書く** — 「何が見えたら意図どおりか」を1文で。
   エージェントは実行して Log や出力を確認し、そこまで自分で検証します。
2. **作業場所を指定する** — `work/` など、リポジトリの例題
   (test/・examples/)の外に作らせます。場所を書き忘れると、
   エージェントが保存先を尋ねてきたり、自分の判断で場所を決めて
   しまったりします(`/make-case` は「work/ に作る」と決めてあるので
   省略できます)。
3. **検証と図化まで頼む** — 「実行して Log の S 列で水収支を確認し、
   結果を図にして」まで書くと、作りっぱなしを防げます。

### 指示の例文

以下は `/make-case` を使わずに**直接指示する**場合の例文です。
`/make-case` が「現象を表す 1 行」だけから定型の一連の作業
(機能選定 → ケース作成 → 実行 → 検証 → 図化)までを行うのに対し、
直接指示では**何を・どのように・どこまで**やるかを自分の言葉で
具体的に書きます — その分、手順や比較の設計を細かく制御できます。

> すり鉢状の地形に 100 mm/h の豪雨を 30 分降らせて、窪地が湛水して
> いく最小ケースを work/ に作って。地形は Python で生成してよい。
> 実行して S 列が降雨量と整合することを確認し、水深の時間発展を
> 図にして。

> 融雪と凍土による浸透抑制が関わる、春先の融雪出水のケースを work/ に
> 作って。使う機能は docs/users_guide/usecases.md を参照。凍土あり/
> なしの2ケースを比較し、凍土ありで地表流出が増えることを図で示して。

> tutorials/chichibu/param_step5.txt をベースに、降雨を 1.5 倍にした
> 感度実験を work/ に組んで。元のケースとハイドログラフを重ねて
> 比較して。

> test/salt の海水浸入ケースについて、潮位を 0.2 m 上げると塩水くさびの
> 到達距離がどう変わるか、work/ で試して数字で報告して。

## 模式ケースから実問題へ(段階的アプローチ)

上の例文のような模式ケース(生成地形+一様な降雨)は練習用では
ありません — **実問題への入口**です。ENCflow の入力は要素ごとに
独立したテキストファイルなので、機構をモデルデータで確認してから、
**データを 1 枚ずつ実世界のものに置き換えて**いけます:

1. **模式ケース** — 生成地形+一様データの小さな格子で、狙った機構が
   動くことと効くパラメータを数分の計算で確認する
2. **実地形へ** — DEM(GeoTIFF / bil)を fn_z に差し替える。窪地の
   処理などの前処理もエージェントに任せられる
3. **実強制へ** — 実績降雨・潮位の時系列、土地利用に応じた粗度・
   浸透マップへ順次差し替える
4. **校正・本計算へ** — 観測(痕跡水位・ハイドログラフ)と比較して
   パラメータを調整し、格子を細かくして本計算に進む

各段で変わるのは入力ファイル数枚だけで、前の段の結果がそのまま
次の段の「期待される挙動」の当たりになります。エージェントへの
指示も段ごとに短く済みます:

> さっきの融雪ケースの地形を、この DEM(dem.tif)に置き換えて。
> 解像度と領域はデータに合わせて。模式地形のときと同じ図を作って、
> 挙動の違いを説明して。

## エージェントに守らせること(重要)

リポジトリの CLAUDE.md(エージェントが自動で読む開発規約)にも
ありますが、利用者の作業では特に:

- **test/*/reference を変更しない・`Run.sh -u` を実行しない**
  (回帰テストの基準です。壊すと検証機能が失われます)
- 既存の例題・テストのファイルを上書きせず、**work/ 等の新しい場所で
  作業する**(work/ は .gitignore 済みです)
- src/ のコード変更はケース作成には不要です(頼んでいないのに
  コードを直し始めたら止めてください)

### 壊れてしまったときの復旧

エージェントの変更でリポジトリの様子がおかしくなったら、原因を
探して直そうとするより、**やり直すのが確実で速い**です:
自分の成果物(work/ の中身など)だけ別の場所へコピーして、
リポジトリのフォルダごと削除し、もう一度クローンしてください。
クローンしたリポジトリは「何度でも作り直せる使い捨ての箱」と
考えて構いません — あなたの作ったケースさえ退避してあれば、
失われるものはありません。

## 上手くいかないとき

- エージェントが機能の選び方に迷っていたら
  [用途集](users_guide/usecases.md)を読むよう指示してください。
- パラメータの意味は[全パラメータ索引](users_guide/params_index.md)と
  各章、注釈付きの実例は [examples/List_samples](../examples/List_samples/)
  にあります — 「〜を参照して」と一言添えるだけで精度が上がります。
- ビルドや実行の環境づくり自体も「src で make install して test/wave の
  Run.sh が PASS するところまで確認して」と頼めます。
